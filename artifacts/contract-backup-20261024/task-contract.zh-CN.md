## 1. 为什么先做这份文件

计划书 §10.3 的成功门槛（开发集 50 场约 80%、封存 ≥200 次未见种子且 Wilson 下界 ≥90%）与 §2.2 的版本化配置，都要求分母、场景、判定口径在跑数之前就固定。现在这三样都是空的：探针只证明了「能读状态、能正常输入」，还没有任何可报数的任务定义。先把契约写死，后续 P1/P2 的评测代码才有稳定的输入。

同时本节记录了一条已经发生的变量漂移（§2.3），它必须先修掉，否则任何统计都不成立。

## 4. 任务 T1：Mom Arena 定义

| 字段 | 值 |
|---|---|
| `task_id` | `t1-mom-arena` |
| 类型 | Boss Arena（隔离测试战斗能力，计划书 §2.1 首个里程碑） |
| 起点 | 已声明的角色、装备、血量、资源与 Boss 房场景（初始化方式见 §7） |
| 成功条件 | 在正常战斗规则下击败 Mom，满足 D31 与 §5 判定器，且未触发 §6 的剔除条件 |
| 失败条件 | 角色死亡且未正常复活完成；超时；判定器判定非目标击杀；崩溃 |
| 时间约束 | 实时闭环（D12），**评测中禁止暂停等待规划器**；Boss 战计时从初始化完成后的第一个更新帧开始 |
| 装备范围 | Arena 固定装备，且必须在每次运行记录里写出具体清单（不得默认强装，也不得与 Full Run 成绩混报） |
| 禁止项 | 无敌、改伤害、直接杀敌、传送、改位置/速度、改碰撞；`EXEC_CONSOLE` 在评测会话中被禁用（见 §6.4） |

**待确认的数值（会直接进入判定器）：**

- 角色起始状态（血量上限、红心数、伤害、泪速、速度、幸运）。
- 固定装备清单（建议：无收集品、无主动道具、0 炸弹/0 钥匙/0 硬币，仅初始泪弹）。
- 超时上限（建议先按「Boss 战游戏时间 180 秒」占位，实测定完后改）。
- Boss 实体 `type` / `variant` / `max_hp` 等标识 —— **不得凭记忆填写**。填写方式：在 Boss 房用 `ENEMIES` 通道采样，记录 `id/type/variant/hp/max_hp` 并附一次运行 trace 路径。计划书 §10.1 明确要求目标 ID 由版本适配器冻结。

## 5. 成功判定器契约（D31 的可执行形式）

判定器必须是独立模块（计划书 §10.1、§9 的 `evaluation/`），**不得读取控制器内部状态，也不由控制器自己报告胜利**。

| 规则 | 内容 |
|---|---|
| R1 目标生命周期 | 目标实体（按冻结的 type/variant 匹配）必须从「存在且 hp>0」转为「hp≤0 / 从 ENEMIES 消失」，且该转换发生于 Boss 战计时区间内 |
| R2 交叉证据 | 优先采用游戏事件（`EVENT`：Boss 死亡 / 房间清理）；事件通道缺失时，用「目标实体生命周期 + `ROOM_INFO.is_clear` + 角色状态」三者交叉验证，且必须在报告中标明所用证据等级 |
| R3 存活口径 | 角色存活，或死亡后由**游戏自身**复活机制完成并恢复可行动；复活道具的来源与使用必须记录 |
| R4 同时击杀与死亡 | 目标消失与角色死亡落在同一确认窗口内：默认判 **失败**，单列 `outcome_reason=simultaneous_death`，不得算作成功 |
| R5 过场与结算 | 击杀动画、过场、结算界面不计入 Boss 战计时；「出现奖励」「房间空了」不足以单独证明击杀 |
| R6 辅助证据 | 截图 / OCR / LLM 复核只作辅助，不得作为唯一判定来源 |
| R7 确认窗口 | 击杀后需在 `confirmation_window_ticks` 内观察到 R1/R2 证据；具体 tick 数待 P0 第 4 项测完延迟后写死（先用 `60 ticks` 占位，并在报告标 `provisional`） |

判定器输出至少包含：`run_id, task_id, outcome(win/lose/abort), outcome_reason, evidence_level, judgement_source, boss_first_frame, boss_dead_frame, player_dead, revived, assist_profile, seed`。

## 6. 分母、剔除与记录

### 6.1 分母规则

- 所有**启动过**的评测运行都进分母，包括崩溃、超时、卡死、人工接管、连接失败。
- 唯一允许剔除的条件是「外部无效」：游戏无法启动、模组未加载、TCP 未建立、存档还原失败。剔除必须逐条记录数量与原因。
- 种子聚类：同一 seed 的重复运行只用于测随机性/可复现性，不作为独立泛化证据；按 seed 聚合或聚类自举（计划书 §10.3）。

### 6.2 每次运行必须落盘的记录

`run_id, task_id, seed, assist_profile, init_method, init_commands, init_state_snapshot,
controller_version, planner_version(prompt 版本), knowledge_version,
per-frame observations（可关键事件环形缓存）, applied_actions（含生效 tick）,
skill boundaries, damage events, death/revive events, outcome + outcome_reason,
judgement evidence, save_hash_before, save_hash_after`

### 6.3 报告口径

点估计 + Wilson 95% 区间（下界同报）+ 分组统计（不同角色/Boss/装备不合并）+ 「有效运行中的策略成功率」仅作诊断，不替代总成功率。

### 6.4 辅助政策的代码化（D06）

- 评测会话只暴露：状态订阅（白名单通道）+ `send_input`。
- 评测会话**禁止**：`EXEC_CONSOLE`、`CONFIGURE_SENSOR` 中放宽采集范围的命令、控制模式切到非 `FORCE_AI/MANUAL` 之外的状态、任何改血量/改伤害/传送类调试命令。
- 训练会话提供独立入口（计划书 §2.3：「训练管理命令置于独立接口并在评测会话禁用」）。
- 每次运行记录 `assist_profile` 与所有辅助动作，报告里单列。

## 7. Mom Arena 场景模板

三种初始化机制，按代价从低到高。**无论选哪种，必须在每次运行记录中写出 `init_method`、具体命令或存档哈希，并声明初始状态，不得默认为「合法配置」。**

### 机制 A：游戏内控制台设置（建议首选）

- 前置：`options.ini` 设 `EnableDebugConsole=1`，启动带 `--luadebug`。
- 候选命令：`stage <N>`（切章节/难度）、`goto <房间>`（跳房间）。Mom 所在的楼层与房间标识**必须在实机上核对**，不得照抄攻略。
- 已知未解决问题：2026-10-24 08:56 的探针用 `goto s.error.21` 时，Lua 返回 `{"result": "Changed room.", "success": true}`，但 20 秒内 `room_index` 没有变化。`EnableDebugConsole=0` 是首要怀疑原因，**必须先验证**；验证通过前，机制 A 不可用。
- 公开声明：初始化在计时开始前完成；评测会话禁用 `EXEC_CONSOLE`（§6.4）。

### 机制 B：继续存档（建议作为回退）

- 前置：提交一份「已在 Boss 房前」的存档副本，每次运行前复制到固定槽位，运行后还原。
- 必须记录 `save_hash_before/after`，并在还原后核对哈希一致。
- 风险：continue save 不等于任意帧快照（计划书 §4.4），重放误差必须实测并记录。

### 机制 C：从楼层起点正常推进（最昂贵，零注入）

- 用于 Full Run 子集或机制 A/B 可信度存疑时的对照。不修改任何东西，但每次运行成本高。

**选择门槛：** 机制 A 通过验证前，P2 的开发集用 B；A 验证通过后 A/B 做一致性对照——同一 seed 下两种初始化方式的首帧状态差异必须在报告里给出。

## 8. 种子策略

| 类别 | 规则 |
|---|---|
| 开发用种子 | 可见、可反复使用，用于调参；清单与用途写进 `configs/seeds/dev.yaml`（待建） |
| 封存用种子 | 一次性生成，生成后仅记录哈希与数量，调参期间不得查看；只在发布候选时使用 |
| 已用过的验收种子 | 一旦用于调参即退出封存集合，需补充新的一批 |
| 记录 | 每次运行记录 `seed`；同种子≠同轨迹（动作分叉后随机流不同），报告中标注 |

## 10. 版本与变更流程

1. 本文件与 `configs/task/mom-arena.yaml` 一起版本化；改动必须同时更新两边并递增 `schema_version` 或 `contract_version`。
2. 冻结后，任何影响分母或判定口径的改动都视为**新任务版本**（如 `t1-mom-arena@2`），旧数据不得与新版本混合统计。
3. 每次实机运行把上述版本的哈希写进运行记录，保证「这批数据属于哪版契约」可查。
