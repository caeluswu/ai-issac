# 任务契约 v0.5（草稿）

日期：2026-10-25。机器配置为 configs/task/progression.yaml；两者须同步修改，冲突时暂停评测并修正。

## 1. 任务边界

| 项 | 已定内容 |
|---|---|
| 游戏 | 当前实测为 Windows 上的 Repentance 原版 v1.7.9b.J835；更换构建需重验接口 |
| 存档 | 使用项目方确认的全解锁存档槽 1；受保护副本、哈希与声明见 configs/task/save-baseline.slot-1.json，解锁内容尚无自动验证 |
| 顺序 | M1 单个战斗房间的底层组件集 → M2 单层完整流程 → M3 第一层开局至第六层 Mom |
| 种子 | 正式评测使用预先生成并封存的随机种子；固定种子仅用于调试和确定性回归 |
| 控制 | 底层为显式、可中断的组件化状态机；DeepSeek LLM 依据武器、房间和道具选择已注册组件并填写参数，负责较长时间尺度的规划 |
| 观测 | 允许读取结构化实时游戏数据，记录实际启用字段和辅助档位 |
| 战斗 | 验收中仅通过正常移动、射击和游戏机制道具击败敌人 |
| 记录 | 每次运行由独立记录器保存调试包，包括伤害来源、资源变化、组件选择和参数；失败、崩溃和人工接管也要留痕 |

“妈腿”在本契约指 Mom，不是 Mom's Heart、Mother 或 It Lives。M3 是从第一层正常开局，逐层推进到第六层并击败 Mom；具体楼层和实体标识须在此构建中采样确认。

SocketBridge 实机探针已证明状态、正常移动与射击、停发释放输入及正常过门可用，见 docs/control-mvp-live-validation.zh-CN.md；首房控制器已完成一次正常出门、DeepSeek 配置与自主清房的实机闭环；这不构成稳定胜率或楼层规划能力的证明，实测结果见 docs/phase-1-live-validation.zh-CN.md。

## 2. 分阶段任务与成功事件

| 任务 | 起点 | 成功事件 | 交付重点 |
|---|---|---|---|
| M1：m1-single-room | 每次只处理一个战斗房间；从预先定义的房间/敌人范围和随机种子抽样，固定角色、难度与初始装备范围；初始化结束后计时 | 房间目标敌人通过正常战斗被清除，房间清理信号成立，角色存活或完成游戏内正常复活 | 导航、目标选择、瞄准射击、躲避、障碍处理、松键、卡死恢复等状态机组件；同时评估失血和资源代价 |
| M2：m2-single-floor | 指定楼层入口正常开始 | 清掉该层 Boss，并通过正常流程进入下一层，角色可行动 | 跨房导航、道具和资源决策、跨层状态迁移 |
| M3：m3-floor1-to-mom | 第一层正常新局开局，连续推进 | 在第六层正常击败 Mom，角色存活或正常复活完成 | 长途路线、构筑管理、风险预算和稳定性 |

M1 是普通单房战斗控制目标。Mom Arena 可作为独立的 Boss 战诊断场景，不能用它代表 M3 通关率。三项任务分开记录、分开报数。

M1 的建议门槛是封存随机样本中 100 次有效启动至少 90 次成功，并列出所有失败、断连和人工接管；这是待冻结的工程目标。胜率必须与每房非主动失血、主动生命支出、炸弹/钥匙/主动道具等资源消耗、耗时和剩余血量同报。严重失血的“通关”不算优质控制。房间分布、角色、装备、初始血量、超时及各指标阈值尚待冻结。M2、M3 先测真实基线，再分别确定稳定门槛。

### 3.1 运行环境选项（冻结）

`options.ini` 的下列项属于运行环境冻结项。自动启动器在游戏停止时备份并配置，正式开始动作前核对运行条件；计时期间不修改这些选项。

| 选项 | 冻结值 | 理由 |
|---|---|---|
| `PauseOnFocusLost` | `0` | 后台运行时继续推进游戏更新与状态通信。 |
| `EnableDebugConsole` | `1` | 仅用于计时前初始化；评测期间不向规划器开放调试权限。 |
| `Fullscreen` | `0` | 窗口模式，便于观察与切回。 |
| `VSync` | `1` | 固定渲染环境。 |
| `MusicEnabled` | `0` | 固定音频环境。 |

移动与射击经模组输入缓存进入游戏，不要求窗口持续在前台。原生暂停及启动菜单使用操作系统键盘输入，需要短暂激活游戏窗口，发送按键后立即尝试恢复原前台窗口。窗口通过可执行文件完整路径、进程 ID 与所属窗口联合定位；多个匹配进程、窗口激活失败或按键前焦点不符时中止，不能删除这些校验来实现后台控制。

游戏可以被其他窗口遮挡，但不要最小化。暂停通信依赖渲染回调，最小化可能导致心跳中断。失焦不触发任务中断；断线、观测过期、死亡、换房和人工切回 MANUAL 仍触发控制保护。控制与战斗耗时以游戏更新帧为依据，窗口激活不作为战斗计时起点。

自动入口为根目录 `run-first-room.ps1`，或使用项目 Python 环境运行 `run_first_room.py`。启动器正常关闭已有单个游戏实例、备份选项与存档、同步模组，使用游戏目录作为工作目录启动指定构建，并通过新鲜结构化快照核对任务初态。存档备份不是已验证的全解锁基线。详细操作、失败语义及证据格式见 docs/phase-1-runbook.zh-CN.md。

## 4. 分层控制接口

### 4.1 底层状态机

底层依据最新可用观测按游戏更新帧生成正常输入，并保留观测过期与动作 TTL 保护。首批组件至少包括安全移动、目标选择、不同武器的瞄准/射击、弹幕与接触危险规避、障碍绕行、停火/松键、门口对齐、清房确认和卡死恢复。每个组件在注册表中声明适用武器/道具类别、前置条件、参数 schema 与上下界、终止条件、失败原因和最大持续帧数。换房、死亡、断线或上层取消时立即中断并释放输入；失焦不中断（见 §3.1）。

建议房间状态为 WAIT_READY → ASSESS → ENGAGE / REPOSITION / EVADE → VERIFY_CLEAR → EXIT；RECOVER 与 SAFE_STOP 可从任何状态进入。组件的内部闭环仍由本地状态机负责，LLM 不输出逐帧方向。M1 同时保留本地规则组件选择器作为基线和故障回退；两种上层复用相同组件与观测。

### 4.2 DeepSeek 上层

M1 中，DeepSeek 在进入房间、武器/道具改变等事件上，从当前合法组件注册表中选择武器控制、移动和战斗组件，并依据房间、敌人、道具及血量填写受约束参数。M2 扩展到楼层路线、房间顺序、拾取、资源与道具使用、进入 Boss 房的时机；M3 延伸至跨层构筑与长途风险预算。请求由进房、清房、发现道具、血量或资源显著变化等事件触发，不逐帧调用。输入为结构化摘要、当前武器语义和候选组件；输出为项目约束的 JSON 计划，注明组件 ID、参数、目标、所属房间/观测版本和失效条件。

计划须通过组件存在性、武器兼容性、参数 schema 与范围、资源、可达性以及房间/版本一致性校验。LLM 不能创造未注册组件或修改底层安全界限。超时、格式错误、旧结果或服务不可用时，底层继续保守的本地闭环，随后用本地规则选择器回退；网络等待不得阻塞逐帧控制。具体模型、接口、超时、提示词版本和单局预算在接入时配置。凭证不入仓库和日志；记录脱敏请求摘要、响应、组件与参数、校验结果、延迟及用量，并与相同底层的规则选择器配对对照。

### 4.3 观测与权限

可用 SocketBridge 的玩家位置/属性/血量/库存、敌人、弹幕、房间信息/布局、拾取物和交互对象等结构化实时通道。“收到通道”不等于字段已校准；每种字段的有效性、刷新频率、时间戳和缺失情况都要记录。默认使用当前房间及已探索信息。若未来开放未探索房间、隐藏门、Boss 内部计时或未来随机信息，需另设辅助档位并单独报数。

评测只开放状态订阅、正常输入和受会话控制的 FORCE_AI / MANUAL 切换。训练及初始化命令使用独立入口；不能靠提示词限制 LLM 调试命令。上层下发技能目标，不直接绕过底层安全控制发任意游戏命令。

## 5. 判定、分母和逐次调试包

独立判定器只读游戏观测、事件和轨迹，不相信控制器自报胜利。M1 用敌人生命周期与房间清理信号交叉确认；M2 还需 Boss 完成与真实跨层；M3 需确认本构建的 Mom 实体及击败证据。Boss type/variant、多实体聚合与确认窗口待实机采样。若完成与死亡同时发生，默认失败；游戏内正常复活完成可记成功但须注明。截图、OCR、LLM 仅能辅助复核。

一次运行在成功初始化并启动控制时进入分母。此后死亡、超时、断连、崩溃、卡死和人工接管均计入；只有启动前的外部环境故障可按预先定义的原因剔除，但也要记录数量。报告按随机种子、房间类型、武器类别分组，给出成功次数/启动次数、剩余血量、受伤、资源消耗、耗时和失败原因。

非主动失血（敌人接触、弹幕、环境伤害及其他未预先授权的生命损失）在局部动作评分中施加惩罚，并在验收报告中单列。主动生命支出须在行动前由合法策略明确授权，记录原因、预期收益和实际代价；它不计作控制失误，但仍计入生命资源预算。事后不得把受伤改标为“主动”。具体惩罚权重、不同心种的换算和生存优先级由实机基线确定，不能为了缩短战斗时间而奖励高风险失血。

独立记录器在任务初始化时创建不可覆盖的 artifacts/runs/<run_id>/，边运行边追加、定期刷盘；异常退出时外层守护补写最小结果，保留已落盘轨迹。记录器和结果判定器不依赖 LLM 自报状态。每次运行至少保存：

1. manifest.json：任务及契约哈希、游戏/模组/控制器/提示词版本、种子、存档槽位和前后哈希、角色/难度/装备、初始化方法、结构化字段白名单、辅助档位和起止时间。
2. trace.jsonl：带游戏帧和单调时钟的观测摘要、实际生效动作、状态机转移、组件起止与参数、房间/楼层切换、受伤来源及心种、主动生命支出、库存/资源变化、死亡/复活、连接状态和观测年龄。高频实体可压缩，但必须保留故障前后窗口。
3. planner.jsonl：若调用 DeepSeek，保存脱敏请求摘要、结构化响应、组件选择与参数、校验与回退、延迟及用量；绝不记录密钥。
4. result.json：独立判定的 win / lose / abort、原因、证据等级、关键帧、耗时、非主动失血、主动生命支出、资源净变化、剩余血量、人工接管及日志完整性。

记录机制的交付门槛：模拟异常中断后仍能读出 manifest、已完成事件及故障结果；随机抽查运行可从日志重建组件选择、参数、动作、失血和判定证据。录像/截图不是每次运行的硬性要求；结构化数据解释不了的失败需留画面证据。批量评测前配置日志保留期限与磁盘上限。
