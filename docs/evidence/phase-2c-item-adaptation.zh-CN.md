# M2-C 有限道具适配与妈妈的菜刀实机证据

## 范围与判据

环境为忏悔原版 `1.7.9b.J835`、Isaac、全解锁槽 1。开发夹具使用固定种子 `3BYH A82R`，在无怪初始房通过控制台设置构筑或生成 114 底座；正式战斗仅使用普通移动和射击输入。这些运行证明控制链路可行，不构成随机局胜率或速度优势估计。一次真实伤害的依据是 `KNIFE_DAMAGE_ATTEMPT` 与后续可见敌人血量下降或死亡共同出现；回调本身只表示尝试。底座拾取和控制台直接给予库存分别标记。

妈妈的菜刀是独立武器家族。Lua 记录刀身份、蓄力、飞行、距离和伤害来源；Python 按实际刀实体及面板组装批量候选；常驻 QuickJS 执行 DeepSeek 编写的蓄力、放刀、回程与站位策略。原始 `EntityKnife.Charge` 在持刀阶段观测为零，模型输入另有由已确认按键和空房校准推导的 `charge` 估计，并保留原值 `engine_charge`。普通实体速度在飞行时观测为零，使用刀专有标量速度。这两个值是 J835 实测现象，不能误读为通用游戏规则。

## 模型来源和现场结果

已发布模型的源码哈希为 `71c0c8af6ce3b51750765caa8cfc7bc21db933e9c53deac79a4c2f692bb03e30`，见 [`skills/weapon.moms_knife`](../../skills/weapon.moms_knife/71c0c8af6ce3b51750765caa8cfc7bc21db933e9c53deac79a4c2f692bb03e30/manifest.json)。`source.js` 与原始 DeepSeek `model-response.json` 由清单哈希核对；开发 Agent 提供宿主 SDK 和观测，并未将手写菜刀打法冒充模型输出。初始三次生成请求中，第一次 JSON 不可解析，第二、三次曾因 SDK 的数字字符串 ID 和假值零号候选检查失败。修正宿主检查后，原始回复离线重验，未重新消费生成请求。第二份候选虽清房，但未确认投掷命中，因此未发布；第三份候选通过下述实机判据。

一次预算内追加的[战后模型反馈](../../artifacts/runs/m2c-knife-20261027T155813689909Z/knife-model-feedback.json)选择 `keep`，未建议为单次成功进行同型改写；原始回复与用量在 `artifacts/item-adaptation/feedback/`。开发审核：保留建议合理，但它把“0 半心损失”解释为可能对应敌人死亡伤害，这混淆了玩家失血与敌人血量，不能采纳这句解释。确认的刀源命中与清房来自原始轨迹，而非模型自评。

## 预算和后续边界

持久账本位于 `artifacts/damage-attribution/budget.sqlite`：归因 3 次、菜刀生成 3 次、战后反馈 1 次，合计 7 次实际请求；第四次菜刀请求由用户授权追加并单独留痕，未重置历史。模型反馈是保留决策，不是实机修订成功。再优化菜刀站位应先利用现有横向偏差轨迹，定义新判据后做一次针对性试验；不为重复固定种子清房增加无意义的付费批次。完整随机运行、跨层道具保持与 69+114 组合均需另行验收。
