# M2-B 实施计划：DeepSeek 编写、验证与复用机制程序

日期：2026-10-27。状态：方案，尚未实施。代码审查基线 `740c6eb`；M2-A 的成功范围及失败见 [验收证据](evidence/phase-2a-validation.zh-CN.md)。本文件维护 M2-B 的范围、实施顺序、预算与验收；机制分类和长期扩展原则由 [组件开发设计](item-knowledge-and-skill-evolution.zh-CN.md) 维护，已有 DTO 与输入权限分别由 [组件合同](component-contract.zh-CN.md) 和 [任务契约](task-contract.zh-CN.md) 维护。

## 1. 目标与推荐决策

交付一条完整链路：**遇见能力缺口 → 查询适用资料和本地证据 → DeepSeek 编写新程序 → 宿主独立检查 → 实机试用 → 发布到技能库 → 另一个进程直接复用**。模型选择现成组件或调整参数不算完成；工程侧写好道具算法再交给模型抄写也不算。

首例推荐 **巧克力牛奶（收藏品 69）的蓄力与释放时序**。它能验证局部状态、输入反馈、条件分支和释放逻辑，覆盖后续更多武器的共同扩展需求。选择它不等于宣称当前已能观测蓄力；B0 必须先证明该机制可以可靠测量。

| 项目 | 首版决定 |
|---|---|
| 游戏与角色 | 原版 Repentance J835、Isaac、全解锁槽 1，沿用当前启动与桥接 |
| 模型产物 | L1 类型化有界 AST，由宿主解释执行；这是程序，不只是组件 ID 和参数 |
| 新职责 | 一个可替换的 `WeaponTiming` 程序；沿用现有移动、目标、几何、避险和独立 Judge |
| 首例构筑 | 基础 Isaac 与 69；105 保留但不使用。额外修饰、饰品、临时效果默认拒绝，支持条件按实测冻结 |
| 首例战斗 | 一个记录完整初始化的普通战斗房间，使用正常移动和射击清房 |
| 复用 | 结束首个进程，启动第二个进程，从技能库加载相同程序哈希并实际执行，不再请求生成 |
| 上层规划 | 仍使用既有有预算的房间规划；代码开发与房间选组件是两个独立服务 |
| 暂不做 | 全道具、复杂协同、Tech X、错误道具、Eden、Wasm、通用 Python 沙箱、自动批量主动实验、胜率或竞速研究 |

如果 B0 证明现有辅助边界下无法可靠建立蓄力反馈，先报告缺失字段及补充成本。可以在**调用模型之前**明确改选丘比特之箭（48）的穿刺多目标命中计算，但那只证明非平凡的无状态程序扩展，不能据此宣布状态机扩展完成。默认执行目标仍是 69；不在失败后悄悄降低成功条件。

M2-B 不重复要求完整首层，也不证明新增道具已经适配所有房间。M2-A 的默认普通泪弹路径必须保留，后续 M3 再扩大组合与连续对局覆盖。

## 2. 代码基线评估与必须补齐的缺口

| 当前实际实现 | 对 M2-B 的影响 | 处理位置 |
|---|---|---|
| `components.py` 的注册表、异常回退和 `component_validation.py` 的输出校验 | 可以拒绝错误结果，不能中断无限计算；不能直接运行不受信任的 Python | B1–B2 的有界解释器 |
| `FrameObserver.begin_frame` 与 `WeaponAdapter.propose` 已分离 | 适合扩展有状态组件；仍需防止多个候选重复推进状态 | B2 的已执行输入反馈与事务 |
| `tests/test_components.py` 有模拟蓄力武器和状态生命周期测试 | 只证明接口能扩展，不证明 69 的真实行为可控 | B0 观测探针与 B6 实机 |
| `builds.py` 拒绝未知收藏品，现有普通泪弹收益与射速模型不理解蓄力 | 仅增加道具白名单会让错误模型继续运行 | B3 的语义解析、时序适配与收益边界 |
| `catalog.py` 使用已有注册规格及版本上下文 | 尚无模型产物的校验、原子注册和持久发布 | B5 的候选库与受控装载 |
| 当前 Lua 导出 `MaxFireDelay` 等属性，未导出经校准的蓄力进度 | 不能把普通射击间隔或发包次数当作真实蓄力 | B0，按缺口最小增加观测 |
| 固定 EID 包的 `rights.ai_input=unknown` | 开发用途查询会去掉正文；当前不能直接得到可交给模型的说明 | B0 的资料准入 |
| M2-A 的 `FloorPlanner` 使用单阶段、无工具调用的紧凑规划 | 已压低日常费用；不应把开发循环塞回每个房间的规划请求 | 独立 `MechanismDeveloper` 与独立预算 |

**不能保证模型不犯错。** 可实现的是：程序权限和计算量受限，错误先被独立检查拒绝，实机效果单独核验，失效不绕过控制内核。程序“类型正确”不代表打法正确，EID 文本“解析完整”也不代表游戏机制已经实测成立。

## 3. B0：先确认资料和原版可观测性

### 3.1 资料准入与知识真实性分开

当前包为 `eid-16b584b65a6e506666e0cf71`，上游固定提交为 `8b59d00c6828e333294639ad2b2b6875eae821cb`。本地 SDK 根据用途过滤正文：`component_development` 在 `ai_input=unknown` 时得不到 EID 正文。**这是本项目元数据和 SDK 的保守默认，不等于已经查明 EID 禁止模型使用。**

先核对固定版本的 [上游项目资料](https://github.com/wofsauge/External-Item-Descriptions/tree/8b59d00c6828e333294639ad2b2b6875eae821cb)、文件说明与来源规则，记录适用结论和依据。若能够明确本地开发用途，生成带有该用途策略和证据引用的**新不可变包**，保留旧包；不能原地改 manifest，不能借 `display` 查询绕过开发用途过滤。正文的模型输入与再分发是不同用途，不互相推断。

若用途仍无法确定，不把它变成整个工程停工的理由：宿主、解释器与实测可继续；模型输入可采用独立编写、绑定实际观测的本地机制摘要，明确其来源，不冒称 EID 说明。EID 到模型的完整通路在这种情况下仍记为未交付，不能用其他资料替代后宣称该项通过。

允许模型读取的 EID 说明标为未审查的来源陈述；运行接口和数值边界来自当前构建观测。模型知识、EID 陈述、本地测量、人工确认与反例分别保存。材料中的操作指令不能改变开发权限或测试标准。

### 3.2 最小机制探针

不调用模型，使用记录完整的开发场景，比较基础泪弹与拾取 69 后的短按、持续按住、释放及输入中断。初始化命令只在计时和正式控制开始之前使用。

探针需要建立以下证据，而不是预设某个原版 API 必然可用：

1. **输入与游戏更新对齐**：动作 ID、接受结果、引擎输入覆盖实际提供的值、对应游戏更新帧。TCP 发送成功或命令接受不等于玩家已经持续蓄力；补充输入应用观测时说明其能证明到哪一层。
2. **出弹反馈**：新己方泪弹的稳定实例 ID、出生帧、来源、方向、速度、尺度及可用伤害字段；必要字段逐项验证可读性和归属，不用其他实体替代玩家泪弹。
3. **时序与收益**：不同按住长度的出弹、释放延迟与可观测效果，形成有限区间的校准配置。没有可读进度时可以采用带误差边界的输入历史估计，但必须用实测出弹核验；不能仅靠模型推断。
4. **中断后果**：暂停、TTL 到期、断线、换房、停止与取消是否产生释放射击，哪些状态需要重置，是否存在观测缺口。暂停不计为持续蓄力时间。
5. **支持判定**：69 在本构建的实际 `weapon_type`、库存和属性变化；不能假设一个新道具一定有一个新的引擎武器类型。

产物为 `artifacts/mechanism-probes/<probe_id>/` 下的 manifest、事件轨迹、校准结果和失败记录；脱敏结论写入版本化证据。只有能对齐“输入—状态估计—实际释放与出弹”，才进入首例生成。否则先补观测或说明无法确认之处，不付费让模型猜。

## 4. 执行架构与模块边界

```text
未知道具遭遇 → 能力缺口任务 → 资料/证据快照 → MechanismDeveloper
                                                ↓
                                    SkillCandidate + 模型测试建议
                                                ↓
                           类型/预算/独立语义检查 → shadow → trial
                                                ↓
                                       不可变 SkillPackage
                                                ↓
已确认暂停边界 → BuildResolver / Catalog → WeaponTiming → 既有武器适配器
                                                           ↓
                                      既有求解器/安全约束/唯一输入通道
                                                           ↓
                                    已应用输入与下一帧观测 → 状态提交
```

建议新增 `SocketBridge/python/mechanisms/`，承担程序合同、AST、解释器、通用原语、开发器、验证器和技能库；不是新增第二套战斗系统。小模块可同文件维护，按实际复杂度拆分。

| 模块/接缝 | 工程侧负责 | DeepSeek 负责 |
|---|---|---|
| `contracts / ir` | 类型、单位、AST、输入输出 schema、版本、限额 | 按合同提交候选 |
| `primitives` | 有界数学、向量、基础几何、只读观测和反馈；不预置完整道具打法 | 使用原语组合新逻辑 |
| `evaluator / runtime` | 燃料、状态隔离、事务、错误处理与输出校验 | 声明有限状态和程序分支 |
| `WeaponTiming` 接缝 | 与现有攻击提案、收益和监督器连接 | 蓄力状态转移、何时保持/释放/重定向的算法 |
| `developer` | 资料裁剪、实际请求总账、有限修复、脱敏溯源 | 初始程序与针对失败的修复；可提出原语缺口 |
| `validation / store` | 独立断言、发布、版本、适用性与隔离 | 提交假设与建议测试，不能批准自己 |
| 安全与判定 | 输入 TTL、避险、资源授权、危险边界、Judge、日志 | 无修改权限 |

通用原语可以计算距离、求有界交点、读取反馈；不能提供已经完成的 `chocolate_milk_strategy()` 或整套 `charge_then_release()` 再把一次函数调用算作模型编程。原语不足则返回 `requires_host_primitive`，说明为何通用，工程侧补接口后再生成。

### 4.1 程序输入与输出

以下是新增合同的设计字段，实施时纳入组件合同与 schema；不是当前已经存在的公开 API。

| 对象 | 必要字段与语义 |
|---|---|
| `SkillRequest` | gap ID、目标构建/SDK/原语版本、支持与排除条件、资料用途策略、来源/反例引用、校准配置、小型轨迹、允许状态、预算和成功条件 |
| `TimingObservation` | 完整 `ProposalContext`、游戏帧、武器语义与校准修订、只读目标/己方弹体摘要、实际应用输入反馈、当前已提交状态；缺失字段显式标记 |
| `TimingEvaluation` | 当前候选移动速度/瞄准方向、只读状态、可行射击窗口；只能提议动作和状态意图，不能直接发送输入 |
| `TimingProposal` | `hold/release/idle` 意图、合法方向、有限收益估计、原因及有限等待请求；单位、范围和适用前提由宿主检查 |
| `SkillCandidate` | 程序 AST、类型化状态声明、接口/原语版本、机制职责、支持/排除条件、来源与假设、建议测试；不含“已支持”权限 |
| `SkillPackage` | 宿主补充程序哈希、实际模型与请求 ID、作者、数据/校准版本、独立检查、试用证据、发布状态与版本 |

模型不能自授能力，不能伪造上下文、伤害上限或 `WaitEvidence`。宿主根据真实武器状态与进度生成等待凭据；模型填写 `weapon_charge` 字符串不足以让监督器忽略无动作。已有 `max_wait_frames=90` 等宿主上限默认保留，首例若无法在允许范围内实现则判为不支持，而非放宽规则过关。

### 4.2 有界 AST 与帧预算

首版仅支持有限数值/布尔/向量/实体引用、局部变量、条件、有限状态读写、静态有界列表遍历和类型化输出。禁止动态属性访问、递归、无界循环、导入、文件/网络/进程/环境访问和直接输入；不使用 `eval/exec`。

初始上限建议：程序 JSON 64 KiB、AST 512 节点/深度 16、状态 16 个有界标量、单列表 32 个实体，输出不超过现有组件上限。B1 用代表性夹具冻结具体上限和 schema。解析前也限制体积和嵌套，不能等递归解析溢出才拒绝。

解释器对每个节点和原语调用计费；原语内部遍历也必须有上限。**燃料按整个游戏更新帧共享**，包括所有移动/瞄准候选的求值，不能每个 `propose` 重置后累计失控。超量立即停止解释，舍弃未提交结果并记录错误；外层输出校验继续保留。

性能暂以单程序稳态约 2 ms、新增运行部分合计约 5 ms 为本机目标，B2 测量冷启动、重复候选、最大输入与最大合法程序后冻结。指令燃料限制工作量，墙钟测量发现性能问题；普通 Python 进程不能因此声称拥有严格的实时抢占保证。任何原语调用若可无限阻塞，都不符合这个架构。

### 4.3 状态提交与中断

同一帧可能对多个目标、方向、速度调用 `propose`。这些都是假设评估，不能每评估一次就增加蓄力帧数、耗一次资源或推进一次状态。

- `begin_frame` 接纳新观测与去重后的应用反馈；候选求值使用只读快照和临时状态。
- 只有实际选中且确认生效的输入能提交相应状态转移；发送失败、接受但未确认、旧动作和候选淘汰均不能被当作持续按住。
- 反馈按动作序号、帧与上下文关联。重复观测不重复提交，缺失/延迟反馈进入明确的不确定状态；不凭观测跳帧补出不存在的完整输入历史。
- run、floor、room visit、build、技能/目录或校准版本变化时，按照状态范围重置；暂停、断线、TTL 与取消单独记录释放后果。
- 存盘复用的是程序和已验证知识，不是上一个进程仍在蓄力的动态状态。

蓄力武器“清零”可能发射，不能把回退描述成无害松键。存在兼容旧程序时才能回退；没有兼容版本就保留有限避险并明确报告 `UNSUPPORTED_MECHANISM`/受控退出，不能让普通泪弹适配器假装接管。失去连接时仍由 Lua 独立释放输入，并保留其已知释放风险。

### 4.4 武器、构筑与收益接入

不要把 69 加入 `ITEM_SUPPORT` 就算完成。BuildResolver 需要按“引擎武器类型 + 实际效果 + 已验证程序能力”选择语义适配；同一个引擎武器类型可以拥有不同的 Timing。普通泪弹原路径不受影响，未知组合保持拒绝。

宿主继续负责弹道基础几何与风险模型；蓄力程序提供时序意图，收益使用本地校准的区间和宿主上限，避免照搬普通连续泪弹 DPS，或由模型任意报高分抢占选择。收益单位继续使用共同预测窗口内的估计伤害。

已飞出的泪弹按实例独立追踪；不能因切换蓄力状态而丢弃旧弹体的待结算伤害。瞄准、运动继承与释放时刻的速度要对齐；第一版若只能支持较窄的运动/射击条件，须在能力清单中限制，不能泛化为全部 moving attack。

## 5. 开发入口、发布与复用

### 5.1 缺口队列与有限开发

首次遇见未知道具时，正常拾取决策仍默认拒绝并保持避让，记录 `MechanismGap`：道具实例、构筑、缺失能力、房间身份、资料版本、证据和原因。相同能力缺口去重，不能每帧或每个房间重新生成代码。

首版提供独立开发入口消费该队列，允许在已确认的入房/清房暂停边界收集快照并创建任务；没有任务时返回“不需开发”。**暂停并不能隔离错误程序**，它只提供发布与取样边界。开发命令的名称和具体 CLI 在 B4 落地前不作为现有可执行命令文档化。

首个版本不承诺在第一次遇见道具的同一局中完成实机训练、发布和返回拾取。完整链路允许跨进程：正常流程产生任务，开发场景验证，发布后后续正常流程自动发现兼容能力并允许策略重新评估拾取。任务的闭环关联必须保留，不能只交付一个与游戏遭遇无关的代码生成脚本。

开发请求预先收集本地资料和 SDK，只请求一次完整候选，不增加独立“先分析”付费轮次。工具功能先用宿主函数实现，不搭建任意 Shell 或通用 Agent 平台；修复轮仅附具体失败及必要反例。

### 5.2 状态与持久化

生命周期为 `draft → validated_offline → shadow → trial → supported`，失败进入 `rejected/quarantined`。`trial` 是严格匹配开发场景的临时授权，不允许正式自动拾取；`supported` 也只承诺清单中列出的构建与组合。

建议开发过程存入 `artifacts/skill-development/<task_id>/`；通过试用后的不可变程序、manifest、测试摘要和脱敏溯源存入版本控制下的 `skills/<component_id>/<version>/`。高频实机日志仍在 `artifacts/runs/`，不复制入 Git；发布包记录哈希和证据路径。运行目录只保留宿主创建的映射，不信任模型提供的任意文件路径。

发布时先确认边界、释放输入并处理释放后果、重验构筑，再原子更新注册表与目录版本；清理受影响状态、计划缓存及旧异步结果。启动时先验证包哈希、schema、依赖和适用条件，再加载；未知版本或不兼容包不能执行。

另一进程从同一版本加载时记录 `origin=reused`、原生成任务及程序哈希；不自动请求“优化版”。损坏包、上下文不符、错误增加或性能超量触发隔离，不能自动静默改用其他武器语义。

### 5.3 作者与费用证据

保存脱敏的真实请求/响应、实际模型、提示词/SDK/资料版本、候选与每轮修复哈希、独立检查、发布与运行记录。可以规范化 JSON，不得由工程侧语义改写程序后仍标 `author=deepseek`；人工修复标明作者或交回模型重新产出。

首例开发任务默认最多 **3 次实际 HTTP 请求**，包括首次生成、最多两次修复及任何网络重试；不是每个阶段各三次。生成输出单次上限建议 8192 tokens，任务总输出上限 24576 tokens；输入总量上限建议 60000 tokens，由请求前估算与返回 usage 共同记账，usage 缺失记未知，不能记零。具体模型参数在 B4 依据现有传输能力冻结。

预算在任务级持久化，进程重启、超时、网络异常不能重置；预留请求额度后才发送。耗尽时停止付费部分，保留候选和失败，继续可执行的本地工作。开发场景使用本地房间配置，复用不再付费；不为证明 M2-B 自动追加一轮完整首层 DeepSeek 回归。其他规划调用计入单独且预先设置的对局预算，最终报告汇总实际总请求。

## 6. 独立验证与完成标准

验证器由工程侧维护，模型只能提交补充测试。测试失败不能通过改断言、取消危险边界或增加道具白名单解决。

| 层次 | 必须覆盖的行为与失败条件 |
|---|---|
| 语言与权限 | 非法节点/类型/越界/NaN/除零/深嵌套、超燃料、最大列表；没有文件网络与直接输入能力；原语耗时有界 |
| 状态一致性 | 同帧多候选、重复/乱序/缺失反馈、观测跳帧、未生效输入、房间与构筑变化、启动复用后状态归零 |
| 武器语义 | 短按、保持、释放、目标消失、无合法射击窗口、边移动边蓄力、出弹归属、暂停/TTL/停止引起的释放；等待证据不能无限续期 |
| 系统集成 | 未知构筑仍拒绝；兼容程序发布后可被选中；旧上下文失效；无兼容回退明确失败；损坏技能库不能装载 |
| 独立语义 | 模型确实增加条件/局部状态/时序，输出并非普通连续射击或固定预制策略调用；通用测试不能替模型实现道具算法 |
| shadow | 固定轨迹上检验合法性、状态和预算；不得据此断言另一种动作一定清房或减少伤害 |
| 实机试用 | 使用模型程序正常清掉一个战斗房，记录实际保持/释放与新泪弹、清房/存活、损失、卡死与监督事件 |
| 第二进程复用 | 停止原进程，重新加载同一程序，正常实际执行并再次清房；程序哈希一致，生成 API 为零，动态状态从初态开始 |
| 原路径回归 | 本地测试验证无候选/禁用开发时普通泪弹和首层规划路径保持可用；不默认增加付费全层实验 |

实机先使用记录完整的机制初始化，可在开始前生成 69；开始后禁止改血、清敌或修改伤害。初始化与固定种子不算正常随机拾取/通关证据，第二次复用同场景也不算独立随机样本。所有启动、失败、伤害与降级保留，不能只保留最终成功。

首例房间在 B0 选定并记录既有 RoomExecutor 的时间与进展阈值，B6 不临时放宽。**卡死到超时就是失败**；无动作、无有效攻击、无位移、无局势进展需区分。真实且有进度的蓄力只允许有限等待；收益不足、等待无反馈或反复取消仍会触发既有危险边界。若恰有目标不可攻击状态，则须有独立证据，不能用模型解释无限豁免。

实机报告至少包含程序作者/哈希与采用帧、状态转移、实际输入与出弹、清房证据、全部半心损失和资源支出、游戏/暂停/墙钟时间、解释器最大耗时/燃料、等待及回退原因、API 用量。原始伤害不被事后标成“主动实验成本”。

**M2-B 完成需要同时满足**：模型新程序、独立检查通过、实机清房、第二进程零生成调用复用、正常缺口队列与发布能力接通、无候选路径回归通过。只完成运行器或代码生成，均为部分完成；不声称稳定胜率、完整蓄力武器支持或 SOTA。

## 7. 实施与 Git 提交顺序

实施分支建议 `codex/phase2-skill-development`，开始代码工作时创建。各提交以可独立检查为边界，不把尚未实现的设计标成通过。

| 顺序 | 提交内容 | 可检查的出口 |
|---|---|---|
| B0 | 资料用途与版本、最小 Lua 观测补充、机制探针与校准证据 | 明确 69 是否可测、输入反馈能证明什么、EID 开发正文是否可用；无模型调用 |
| B1 | 类型化 AST/schema、SkillRequest/Candidate、SDK 与 WeaponTiming 合同 | 静态拒绝坏程序，合同示例可解析；示例不包含首例完整算法 |
| B2 | 燃料解释器、通用原语、状态事务、共享帧预算 | 对抗性本地夹具通过，同帧多次求值不重复推进；测量并冻结限额 |
| B3 | Timing 接入、构筑语义与能力编译、收益与有限等待 | 本地集成覆盖新旧路径、释放中断、未知组合和不兼容回退 |
| B4 | 缺口任务、独立开发器、持久预算与模型产物溯源 | 假客户端覆盖生成/修复/超时/重启；真实请求暂不必发送 |
| B5 | 独立验证、shadow/trial 授权、不可变库与原子发布/隔离 | 用明确标注的工程夹具程序验证发布重启路径；不能用它充当最终模型程序 |
| B6 | 有预算真实生成、独立检查、实机试用、发布及第二进程复用 | 必要的模型开发请求与全部失败留证，完成标准逐项核对，同步合同和运行手册 |

依赖为 B0 → B1 → B2 → B3；B4 依赖稳定 SDK，B5 依赖运行器和构筑接入，B6 依赖前述全部出口。付费生成集中在宿主闭环通过之后。机制探针可能引入新的源文件哈希，必须同步环境与证据，不能复用 M2-A 的旧模组哈希声明新结果。

检查强度遵循 [协作约定](../AGENTS.md)：每步运行相关本地测试；集成结束运行现有完整单元测试；最后做一轮针对性 diff 审查。实机只执行需要的机制探针和端到端试用，不默认进行消融或批量付费回归。验收证据写入 `docs/evidence/phase-2b-validation.zh-CN.md`，该文件在真实验证后创建。
